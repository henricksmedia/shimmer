# House rules

Collected 2026-09-09 from decisions already made and already followed in this
codebase. Nothing here is new. It is written down because it was scattered
across docstrings, commit messages and conversations, which is why it kept
being asked about instead of looked up.

---

## Words the user reads

**Eighth-grade reading level.** Short sentences, plain words, one idea at a
time. Checked with a Flesch-Kincaid pass; the control naming that shipped
measures FK 4.7–5.9.

**Industry terms as the label, plain language as the description.** A control
is called what a mastering engineer would call it, and the sentence
underneath explains it. Not the other way round: renaming a high-shelf to
"Sparkle Boost" teaches nobody anything and makes the tool harder to
translate to a DAW.

> Tone target · *The tone shape Shimmer aims at: the middle of hundreds of
> finished masters, band by band.*

**Follow DAW convention** where one exists. dB, LUFS, dBTP, Hz, 1/3-octave,
true peak, high-shelf. If a plugin would call it that, so do we.

**No invented jargon, and no AI-slop vocabulary.** "Signal Chain" as a
capitalised product noun is the standing example of what not to do. If a
phrase would look at home in a generated landing page, cut it.

**Say the number.** "About 6 dB duller across 800 Hz to 6.3 kHz" beats
"noticeably duller." A claim without a number cannot be checked, and several
in this project turned out to be wrong precisely because nobody could.

**Never name a third-party service** in code or in user-facing documentation
and help. The one exception is a literal metadata string in a provenance
lookup table, where the name is data being matched rather than prose. Local
working scripts are not covered — a filename has to match the file.

## Comments and docstrings

**Say why, not what.** The code says what. A comment earns its place by
recording the reason, the measurement, or the trap.

**Every constant carries its provenance.** Where the number came from, what
it was measured on, and what would make it wrong. This project shipped two
wrong tone targets, and in both cases the comment stated a conclusion with no
way to check it.

**A comment that states a fact must be checkable.** `mastering.py` claimed
"real masters hold roughly level from 315 Hz to 10 kHz." They fall 15.7 dB.
That one sentence set the direction of everything downstream for weeks.

**Mark confidence.** Distinguish *measured* (a script was run, numbers shown,
command re-runnable), *cited* (a document was fetched and quoted), *read*
(source was read), and *believed*. Almost every error in this project came
from a believed claim written in the voice of a measured one.

**Prefer a derivation to a constant.** If a number can be regenerated by a
committed script, it should be, and the script named where the number lives.

## Documents

**`HANDOFF-CHECKLIST.md` is append-only.** Items are never deleted and never
struck through. Status changes, with a reason. Twice, items were silently
dropped, and both times they were the ones that would have slowed the work
down — that bias is why removal is not allowed.

**Corrections stay visible.** When a finding is overturned, the original text
stays and the correction is added underneath. `BRIGHTNESS-ASSESSMENT.md` §2.1
and §7 both read this way. A document that quietly rewrites itself teaches
nobody what went wrong.

**Write the caveat next to the number, not in a footnote.** A figure that
needs three conditions to be true should carry them.

## Code

**Sound changes only at their proper point in the documented chain.**
Analysis measures and never alters. If a fix seems to belong in two places,
it belongs in neither until the chain is understood.

**No band-aids.** Find the cause and fix it. If the proper fix is large, say
it is large. Do not offer a reduced-scope fallback or a manual workaround as
an alternative — both are rejected, and offering them wastes a turn.

**Never assert a standard from memory. Fetch it.** Every incorrect claim in
this project came from stating a standard, a best practice, or an industry
norm without checking. The reference documents are listed in
`IMPLEMENTATION.md` §6.

**Measure before and after every change**, on the corpus, and show the
numbers. Not "this should help."

**A metric that cannot fail is not a metric.** `purity` scored ~1.0 for
everything for months because it measured where a preset operates rather than
what it removed. Test any new measure against material where the right answer
is known — a finished master should score as needing nothing.

**Tests assert relations, not invented thresholds.** Clean material damages
less than hashed; damage is monotonic in strength; surgical presets sit below
broadband ones. A hard-coded number in a test is a guess given authority.

**A test built from the constant it tests will drift.** One did exactly that
when the tone target moved: the detector was fine and the stimulus had
shifted underneath it.

## Repository

**LF endings.** The repo is normalised; write patch files with `newline="\n"`
and do not add another `text=auto`.

**Working scripts stay out of git.** Analysis and one-off evidence lives in a
gitignored folder inside the repo, next to the data it reads. Preserved, not
published — the repo is public.

**Short, neutral commit subjects.** The body carries the reasoning, the
measurements, and what was left undone. No trailers.

**Stage by path, and read the diff content before committing.** Two agents
have shared this worktree; `git add <file>` takes whatever is in the file,
including someone else's uncommitted work.
